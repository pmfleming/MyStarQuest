Separate Chores and Tests

Plan based only on the project code. No existing docs or plan files were used.

The current implementation treats chores and learning tests as variants of one task system. The requested change is to make them separate in the interface and in Firestore, while preserving the existing daily flow and star-award behavior.

Current Code Shape

The application currently has three bottom tabs from src/lib/tabNavigation.ts: dashboard, rewards, and time explorer. Chore management is reached from the dashboard header via /settings/manage-tasks, not from the bottom tab list.

Chore and test templates are both stored in users/{uid}/tasks. Daily runnable items are both stored in users/{uid}/todos.

Current type Meaning Current collection Daily collection
standard Custom/simple chore tasks todos
eating Dinner chore tasks todos
watertoiletcheck Water and toilet chore tasks todos
math Arithmetic test tasks todos
positional-notation Positional notation test tasks todos
alphabet Alphabet match test tasks todos

The shared behavior is concentrated in src/data/useChores.ts, src/data/types.ts, src/lib/choreParser.ts, src/ui/unifiedChoreDescriptors.tsx, and the scheduled Firebase functions in functions/src/index.ts.

Target Product Shape

The bottom navigation should become four tabs. The clean target is:

  • Chores today's chore list and chore management entry point.
  • Tests today's test list and test management entry point.
  • Rewards existing rewards tab.
  • Time existing time explorer tab.

Chores should include standard/custom chores, dinner, and water/toilet check. Tests should include arithmetic, positional notation, and alphabet match.

Keep the existing dashboard route stable during migration by redirecting /tabs/dashboard to the new chores tab, or by retaining dashboard as the internal id while changing its visible role to chores.

Target Firestore Model

Use separate collections for templates and daily instances. This avoids a cosmetic split where tests are still mixed with chores in the database.

Purpose Collection Type field Source field on daily item
Chore templates users/{uid}/chores choreType n/a
Test templates users/{uid}/tests testType n/a
Today's chore items users/{uid}/choreTodos sourceChoreType sourceChoreId
Today's test items users/{uid}/testTodos sourceTestType sourceTestId

Suggested type split:

  • ChoreType = "standard" | "eating" | "watertoiletcheck"
  • TestType = "math" | "positional-notation" | "alphabet"

Keep shared fields such as title, childId, schedule flags, starValue, isRepeating, and createdAt in both template collections. Preserve type-specific fields only on the relevant collection.

Implementation Phases

1. Split the data types

  1. In src/data/types.ts, introduce explicit ChoreType, TestType, ChoreRecord, TestRecord, ChoreTodoRecord, and TestTodoRecord.
  2. Keep a shared base type for schedule, title, stars, repeating, and created date so the UI does not duplicate generic controls.
  3. Add new Zod schemas for chore snapshots, test snapshots, chore todo snapshots, and test todo snapshots.
  4. Retain legacy parsers for tasks and todos during migration, but mark them as compatibility-only in code.

2. Split the data hooks

  1. Replace useChores() with a smaller useChores() for chore collections and a new useTests() for test collections.
  2. Move createMathTask, createPVTask, and createAlphabetTask into useTests() as createMathTest, createPVTest, and createAlphabetTest.
  3. Keep createStandardTask, createEatingTask, and createWaterToiletTask in the chore hook, but rename the public API to use chore wording where practical.
  4. Split today's derived lists into availableChores and availableTests, backed by separate daily collections.

3. Split the UI routes and tabs

  1. Add a fourth tab to appTabs in src/lib/tabNavigation.ts, using an existing maths icon for the tests tab.
  2. Add a new route such as /tabs/tests in src/App.tsx.
  3. Convert DashboardPage into a chores-only today view, or create ChoresTodayPage and redirect the old dashboard path to it.
  4. Create TestsPage for today's tests. Reuse the existing math, positional notation, and alphabet renderers from src/ui/presetChoreRenderers.tsx.
  5. Split ChoresPage into chore management and test management, or keep one shared management component that receives a kind prop.
  6. Update header buttons and legacy settings routes: /settings/manage-tasks should redirect or be replaced by /settings/manage-chores and /settings/manage-tests.

4. Reuse, then rename, the shared activity renderer

  1. Keep createUnifiedChoreDescriptor initially to reduce risk, but rename its item model to activity/item wording in a later cleanup.
  2. Restrict the chore page to chore types and the tests page to test types before passing items into the shared descriptor.
  3. Move labels like getTestPrimaryActionLabel into a tests-specific module only after the database and route split is stable.

5. Update Firebase functions and rules

  1. In functions/src/index.ts, update generateDailyTodos to read both chores and tests.
  2. Write chore instances to choreTodos and test instances to testTodos.
  3. Update resetTodayTodos to reset both collections, or split it into resetTodayChores and resetTodayTests if the UI needs independent reset buttons.
  4. Extract the duplicated template-to-daily-item mapping code in the cloud function before changing it. That will make the collection split safer and easier to test.
  5. Add Firestore rules for chores, tests, choreTodos, and testTodos, preserving the current owner-only access model.

Migration Plan

Use a compatibility window so existing users do not lose templates or today's progress.

  1. Deploy code that can read the new collections and optionally fall back to old tasks/todos if the new collections are empty.
  2. Run a one-off Firebase Admin migration script:
  • Copy old tasks with type math, positional-notation, or alphabet to tests using the same document id and a new testType field.
  • Copy all other non-legacy old tasks to chores using the same document id and a new choreType field.
  • Copy old todos with test source types to testTodos, preserving completion state, source id, date key, and outcome fields.
  • Copy old todos with chore source types to choreTodos, preserving completion state, source id, date key, and chore-specific fields.
  1. Verify counts per user and child: old task count equals new chore plus test count, excluding already ignored legacy day/night records.
  2. After the compatibility period, remove fallback reads from tasks and todos.
  3. Leave old collections untouched until a final backup and manual verification are complete.
Preserve document ids during migration. The current dedupe logic uses source template ids, so changing ids would risk duplicate daily items.

Testing Plan

  • Update parser tests in tests/unit/lib/choreParser.test.ts to cover new chore and test schemas separately.
  • Add tests for the new type guards and default values in src/data/types.ts.
  • Update descriptor tests so preset test start/check behavior is exercised through the tests path, while standard/dinner/water behavior is exercised through the chores path.
  • Add route/navigation tests proving the bottom nav has four tabs and that /tabs/tests renders the test list.
  • Add cloud-function helper tests for mapping chore templates to chore todos and test templates to test todos. If function tests are too heavy, extract pure mapper functions and unit-test those.
  • Run npm run lint, npm run test, and the functions TypeScript build before merging.

Recommended Order of Work

  1. Create the new type model and parsers behind compatibility helpers.
  2. Split the hooks into chore and test data flows.
  3. Add the fourth tab and the tests page while keeping old routes redirecting.
  4. Update cloud functions and Firestore rules.
  5. Add and run migration tooling against a backup or emulator first.
  6. Remove old mixed collection reads after production data is verified.
