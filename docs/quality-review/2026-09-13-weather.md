# Weather quality lens review

The weather code has **no blocking findings**, but has concentrated complexity and a small set of actionable warnings. The most useful work is to simplify refresh and exploration decisions, tighten the control option types, and move the shared seasonal-image lookup out of the clock feature. The magical artwork already benefits from reuse; splitting static SVG markup merely to lower file-size scores would add little value.

## Main findings

### 1. Refresh is the strongest complexity hotspot

[`weatherStore.ts:69`](../../src/lib/weather/weatherStore.ts#L69), `refresh`: **cognitive 21, cyclomatic 19, effort 93,361**. It combines cache-age/date decisions, retry throttling, request ownership, timeout setup, response publication and failure recovery.

Extract a pure refresh decision from the request lifecycle, keeping cancellation and publication ownership together. Preserve the existing regression checks for stale data, midnight/date rollover, failed requests, StrictMode re-subscription and late responses. Avoid fragmenting the lifecycle into helpers that obscure who owns the active request.

### 2. Exploration carries the most reported effort

[`useWeatherExploration.ts:27`](../../src/hooks/useWeatherExploration.ts#L27): **effort 160,683**, roughly 30% of the weather core's reported effort. Its state updater merges live weather, the draft, temperature rules, wind levels, cloud levels and thunder state inside a React callback.

Move the draft transition into a pure weather-domain operation and leave the hook responsible for state and memoisation. Preserve city reset, live-update isolation, precipitation intensity and the distinction between observed weather and user exploration. This and `refresh` together account for roughly **47%** of the core's reported effort.

### 3. Controls combine selection logic, rendering and asserted indexes

[`WeatherControls.tsx:98`](../../src/components/weather/WeatherControls.tsx#L98): **219 file lines**, component cognitive **11**, cyclomatic **12**. Its leverage-risk score is **96**, driven by **eight assertions**: two type assertions and six non-null assertions. This is a heuristic about those assertions, not proof of unsafe runtime behaviour or a need for more consumers.

Use explicit typed wind/precipitation option tables and centralise bounded selection. Share intensity labels with the exploration description where that removes real duplication. Keep the standard `StepperButton` reuse and the accessible control names. Prefer eliminating repeated decisions over adding generic configuration layers.

### 4. Seasonal image reuse crosses the clock feature boundary

[`WeatherOptionImage.tsx:9`](../../src/components/weather/WeatherOptionImage.tsx#L9) imports `resolveBackgroundImage` from `features/dayNightExplorer/dayNightExplorerBackdrop.ts`. Lens flags **UI importing upward into a feature**.

Move the small, pure seasonal-image lookup into a shared module with a neutral contract, then have both clock and weather consume it. Keep the existing selected-date behaviour and shared assets. This improves ownership without duplicating the resolver or adding a barrel merely to shorten the import path.

### 5. Three typed-lint warnings and three unnecessary exports are quick cleanup

- [`WeatherScene.tsx:81`](../../src/components/weather/WeatherScene.tsx#L81): the custom animation properties use a narrowing `as CSSProperties` assertion. Declare a style type that explicitly includes the two CSS custom properties.
- [`weatherStore.ts:59`](../../src/lib/weather/weatherStore.ts#L59) and line 60: `publish` asserts keys returned by `Object.keys`. Use an explicitly typed snapshot comparison rather than repeated key assertions, preserving the no-change notification guard.
- `WEATHER_MAX_AGE_MS`, `EMPTY_WEATHER_VISUALS` and `WEATHER_LABELS` are used inside their declaring modules but have no external consumers in the snapshot. Remove their **exports**, retaining their implementations. Knip supports these cleanup findings; source search confirmed the local usages.

## Rendering and shared-module observations

`WeatherOptionImage` has a hotspot score of **150** (component cognitive **6**, cyclomatic **7**, render-branch complexity **8**). `WeatherScene.tsx` is **292 lines**. Both still choose between rain, snow, sleet and hail while placing particles. A shared precipitation glyph selector can reduce the remaining repeated branch structure, building on the existing `RainDrop` and `WindRibbon` reuse. Keep scene placement/animation and thumbnail placement local to their renderers.

`WeatherMagic.tsx` has **zero leverage risk**, two consuming modules, and no detected clones. `WeatherThermometer` scores **119** as a component, but has cognitive complexity **5** and cyclomatic complexity **6**; its score is strongly influenced by SVG/JSX density. It is a lower-priority refactoring target than request and draft-state logic.

The ten associated modules are `AsyncButton`, `IconActionControls`, `StepperButton`, `SelectedDateContext`, `ThemeContext`, `dayNightExplorerBackdrop`, `seasons`, `TimeExplorerPage`, `tokens/index` and `themeAssets`. Their findings include:

- Three typed assertion warnings in `themeAssets.ts`, at lines 153, 180 and 183, around `Object.fromEntries`-built registries.
- Two dependency-layer warnings: `tokens/index.ts` imports the UI `Theme` type; `themeAssets.ts` imports the `Season` type from `lib/seasons`. These are type-only edges and need lower priority than the runtime clock-helper dependency. Do not reorganise shared types solely to silence folder-based heuristics.
- `getExplorerBackdropColor` and `getExplorerBackgroundBlend` report effort **74,689** and **66,324**, respectively. They perform similar time-stop searches and are candidates for a shared segment lookup if clock cleanup is taken on separately.
- Shared stepper/action controls have **zero leverage risk**. The existing reuse is worth preserving.
