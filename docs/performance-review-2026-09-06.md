Performance review — 6 September 2026

There are useful opportunities to speed up MyStarQuest without changing image files, image dimensions, fonts, texture resolution, or displayed artwork sizes. Start with the deliberate login delay, the login loading waterfall, and repeated Time Explorer initialization. The website and Capacitor Android app share these React code paths; website transfer savings do not translate directly into Android network savings because its web assets are packaged locally.

This is a review of the current working tree, including the ongoing animal/Teenieping work. No application or asset changes were made.

1. **Remove the 900 ms sign-in delay.** [LoginPage.tsx](C:/Code/MyStarQuest/src/pages/LoginPage.tsx:47) waits after authentication has already succeeded before navigating. Remove the fixed delay, or navigate while a success indication appears in the destination. This removes 900 ms of deliberately added waiting whenever this path runs; it does not change authentication or destination loading time. Verify that fresh sign-in and already-authenticated visits to `/login` reach the intended destination immediately.

2. **Avoid lazy-loading the small login screen after the entry bundles execute.** [App.tsx](C:/Code/MyStarQuest/src/App.tsx:12) defers LoginPage. In the lab run, its chunk and three supporting chunks were requested only around 1.49 seconds. Together they add approximately 4.7 kB gzip beyond the existing entry graph. An eager import is a reasonable tradeoff for the entry screen; alternatively arrange an early route-aware preload. Keep large authenticated features lazy. React invokes a lazy loader when the component is first rendered, which explains this extra loading stage. [React lazy documentation](https://react.dev/reference/react/lazy). Re-run several cold browser samples and compare median paint time and request start times; do not assume the entire 1.49 seconds is removable.

3. **Cache the generated Earth pixels independently of the renderer.** [useSolarSystem3D.ts](C:/Code/MyStarQuest/src/components/dayNightExplorer/useSolarSystem3D.ts:17) creates a new manager on mount and disposes it on unmount. Returning to the tab rebuilds the scene, twelve canvas labels, and Earth texture. [earthTexture.worker.ts](C:/Code/MyStarQuest/src/components/dayNightExplorer/earthTexture.worker.ts:19) fetches and parses the 1.31 MB world dataset and rasterizes it each time. HTTP caching saves transfer but does not preserve the parsed geometry or rasterized result across these new workers. Start with one version-keyed cached result or shared pending computation, retaining the existing 2048 × 1024 texture. One RGBA pixel buffer costs 8 MiB, so bound its lifetime and avoid accumulating copies. Handle transferred ArrayBuffer ownership explicitly. Profile the second and tenth visits: they should not repeat topology parsing and rasterization. Keeping the entire scene alive is a larger alternative with a higher retained-memory cost.

4. **Dispose resources for Points, Line, and Sprite objects as well as Mesh.** [SolarSystem3DManager.ts](C:/Code/MyStarQuest/src/components/dayNightExplorer/SolarSystem3DManager.ts:849) returns early for every non-Mesh during cleanup. The scene includes a Points starfield, twelve Line month ticks, and Sprite month labels. Their geometry/material cleanup is consequently omitted; the orbit line and label textures have separate explicit cleanup, so those are not the missing pieces. Extend disposal by resource capability/type, account for shared resources, and verify label rebuilds too. Three.js requires explicit resource disposal. [Three.js disposal documentation](https://threejs.org/manual/en/how-to-dispose-of-objects.html). The cleanup omission is confirmed; persistent memory growth on a real device has not been measured. Validate repeated tab visits and theme changes with disposal spies and browser/GPU memory inspection.

5. **Make loading policy depend on where and when an image is needed.** [ImageStarFrame.tsx](C:/Code/MyStarQuest/src/components/ui/ImageStarFrame.tsx:54) makes every overview image lazy, including the first visible card. Expose a loading/priority option: load the initially visible image eagerly and give high priority only to the measured largest-contentful-paint candidate; retain lazy loading below the viewport. Browser guidance specifically discourages lazy-loading initially visible/LCP images. [Image loading guidance](https://web.dev/articles/browser-level-image-lazy-loading). In [AnimalTester.tsx](C:/Code/MyStarQuest/src/components/AnimalTester.tsx:427), artwork appears on demand without the next-image preload used by AlphabetTester and SpellingTester. Preload/decode only the next known animal and immediately needed clues during the current round. Do not preload whole catalogs. Check first-card paint and next-round image readiness on a throttled connection; preserve every image byte and dimension.

6. **Load creature collection metadata and mappings on selection.** [AnimalTester.tsx](C:/Code/MyStarQuest/src/components/AnimalTester.tsx:17) statically imports animal, insect, and Teenieping datasets and initializes their catalogs together, although Animals is the default collection. Separate collection adapters into dynamic imports while keeping the shared activity shell available. Preserve a lightweight collection-availability flag instead of importing an entire collection to decide whether its selector is enabled. The 43.9 kB gzip chunk is the current total, not the predicted saving. Measure the resulting default-Animals dependency graph to establish the actual reduction. Asset URL imports do not mean all images download immediately; this finding concerns JavaScript and catalog initialization. Preload a collection only on likely selection, and verify every activity mode after the split.

7. **Keep unaffected records and cards stable during data updates.** [useUserCollection.ts](C:/Code/MyStarQuest/src/data/useUserCollection.ts:64) maps every document into new objects on each snapshot. [StandardActionList.tsx](C:/Code/MyStarQuest/src/components/ui/StandardActionList.tsx:371) renders all cards, while page descriptors and handlers are recreated. A one-item update therefore invalidates much more UI than necessary. Use document changes or an ID-keyed reconciliation cache to preserve unchanged objects, then stabilize props and memoize card boundaries together. Memoization alone will not help when every object/function changes. Profile realistic small lists and a larger fixture before considering virtualization, which could complicate active activities. Also reuse the child balance already supplied by ChildrenProvider instead of adding the overlapping document subscription in [useRewards.ts](C:/Code/MyStarQuest/src/data/useRewards.ts:105). That removes redundant subscription/parsing work; billing savings are not quantified. Keep transactional star-award and redemption checks intact.

8. **Put the school calendar behind an actual shared cache.** [SchoolCalendar.tsx](C:/Code/MyStarQuest/src/components/SchoolCalendar.tsx:26) calls a `run.app` endpoint directly. [functions/src/index.ts](C:/Code/MyStarQuest/functions/src/index.ts:318) fetches a timestamp-busted upstream calendar and parses it for each function invocation. Its public cache header helps client caching, but the direct endpoint does not pass through the project's Firebase Hosting CDN. Add a calendar Hosting rewrite before the SPA catch-all and use its HTTPS URL from Android and the website; preserve an appropriate shared-cache TTL. Firebase supports CDN caching of dynamic responses through Hosting. [Firebase cache documentation](https://firebase.google.com/docs/hosting/manage-cache). An upstream refresh cache can further reduce repeated work. The existing seven-day local cache already makes repeat visits cheap on one device, so this mainly benefits cache misses and new devices. Validate cache hits, upstream request counts, and calendar freshness.

**Secondary items and existing strengths**

The globe reads canvas dimensions and applies full scene calculations on every animation frame ([SolarSystem3DManager.ts](C:/Code/MyStarQuest/src/components/dayNightExplorer/SolarSystem3DManager.ts:271)). A ResizeObserver can remove repeated dimension polling; cache state-derived positions and reuse temporary vectors. Profile this before changing it: rotating stars and city pulses are intentional, and an on-demand renderer would change their behavior. Keep the current texture dimensions, antialiasing, and visual fidelity.

The scheduled daily generator processes users and children sequentially ([functions/src/index.ts](C:/Code/MyStarQuest/functions/src/index.ts:193)). Bounded concurrency and chunked writes are growth opportunities if job duration increases. This is backend batch throughput, not evidence of a current foreground interaction bottleneck.

Already useful: lazy page/activity boundaries, delayed Firestore initialization, persistent IndexedDB data caching, active-child query filters, coalesced optimistic document updates, parallel transaction reads, active-theme font loading, three-item carousel rendering, worker-based Earth rasterization, and globe visibility gating. The clock already updates second-level visuals without rendering the whole React tree every second. Do not repeat older optimization plans that describe these as missing.

The current production output contains about 168 MB of image files across all features. That is packaged content, not the initial website download. No resizing, recompression, format conversion, or reduction of asset quality is proposed. Broad image precaching would compete with the requested performance goal.

**Validation and next implementation sequence**

The production build and 22 tests across six suites passed: dayNightPerformance, DinnerCountdown, useCoalescedDocumentUpdates, AnimalTester, InsectTester, and TeeniepingTester. These tests cover existing safeguards and behavior; they do not measure frame rate or prove the proposed gains.

Implement items 1–2 first, then 3–4 together, followed by image loading and collection splitting. Compare several cold and warm website runs, first/repeat Time Explorer visits, ten tab round trips, clock dragging, and activity progression. Measure Android on a release build on a representative device, including frame times and retained memory. No authenticated performance trace, deployed-site cache inspection, physical Android test, or quantified percentage speedup is claimed by this review.
